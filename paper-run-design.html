设计解读 · paper-run v0.5.0

paper-run 的写作能力边界

这套系统优化的不是「把论文写好」，而是「不造假、可恢复、可审计地把一份稿子跑完」。 写作能力来自别处——底座模型和外部的 agent-writing-harness skill 库。 而实测发现：那套写作方法论并不薄，薄的是送达。 下面是它的输入、13 个阶段、控制器循环，以及 skill 调用链条断在哪里。

13 stages 2 modes · 6 plan profiles 约 10k 行 TypeScript runtime: OpenCode

先回答：它有真正的写作能力吗

分成两半看。这个仓库里几乎没有一行讲「怎么把一段话写好」的内容，而且是刻意的。 src/pipeline/prompts.ts 的注释写得很直白：stage prompt 的职责是定位而非指导， 重复写作技艺会制造「第二套互相竞争的写论文说法」，那正是 harness 警告的边界越权。

但系统确实会写——写作能力来自三处，都不在这个仓库里。

paper-run 优化了什么

作业执行与诚实性

  • ✓ 材料不足时拒绝开写，而不是硬凑
  • ✓ 完成状态由仓库判定，不接受 agent 自称「done」
  • ✓ 任意时刻中断都能从 Git checkpoint 续跑
  • ✓ 人类锁定的字段 fail-closed，改动需显式授权
  • ✓ 每个阶段的耗时、token、成本都留痕
paper-run 没有优化什么

文章本身的好坏

  • ✕ 论证是否成立、故事是否讲得通
  • ✕ 贡献陈述是否有说服力
  • ✕ 行文质量、术语一致性之外的语言水准
  • ✕ 与目标会议审稿口味的贴合度
  • ✕ 「这篇值不值得投」的任何判断
写作能力实际来自

三个外部来源

  • 底座模型——temperature: 0.3，模型换了质量就换了
  • harness skills——section-writing 加 2,586 行 vendor 写作参考、329 行 scientific-writing.md，全在 agent-writing-harness 仓库
  • AGENTS.md 路由表——决定哪个 skill 拥有当前任务

这些资产很厚，但下一节会看到它们大多到不了模型面前。

所以那句判断成立：想提升文章质量，杠杆在 harness skills 和模型选择上，改这个仓库收效很小。 它是作业执行器加诚实性约束，不是写作模型。

证据：所有校验器都只看结构

validators.ts 一共六种 validator。把它们逐个列出来，边界就一目了然了—— 每一种问的都是「东西在不在、脚本退出码是不是 0」，没有一种在问「写得好不好」。

src/pipeline/validators.ts — 六种校验方式及其判定依据
Validator 判定依据 用在哪 能判断质量吗
check_script 跑 harness 的 check-*.py，退出码 0 即通过 几乎每个阶段 否 · 结构校验
file_exists 文件存在，可选 minBytes 下限 BRIEF.md、review-findings.md 否 · 只看字节数
contract_section 契约里某个 ## 标题 存在且该节非空 PAPER.md、EXPERIMENTS.md 否 · 只看非空
dir_has_content 目录下有 ≥1 个符合后缀且超过下限的文件 paper/sections/*.tex ≥ 200 字节 否 · 只看体积
state_file JSON 状态文件存在且可解析 assessment.json 否 · 只看格式
publication_build 构建产物是新鲜的、PDF 有基本结构 publication_build 否 · 只看能否编译
这条边界的实际后果

一篇论证松散、故事讲不通、贡献含糊的稿子，完全可以 13/13 全绿通过， 拿到 candidate tag。校验器看不出区别。

唯一靠近内容质量的关卡是 independent_review——控制器另开一个 OpenCode session， 用 paper-reviewer agent 冷读全文。但它的 validator 也只检查 review-findings.md 存在、≥200 字节、且有 Blocker / Major / Minor 三节。 「这次评审本身做得好不好」同样不在校验范围内。质量判断被委托给了模型， 而模型的判断没有被二次校验。

补充一条实测事实：harness 里其实带了一个可用的散文质量检查器 （check_prose_quality.py，支持 --strict --format json --scope）， 但它躺在 vendor 树里，paper-run 的 runCheck() 够不到——见下一节。

那些写作 skill，真的被用上了吗

这是决定后续所有优化方向的问题。把 harness v0.3.0 拉下来实测后，答案是： 方法论资产很厚，但送达链条大概率是断的。

vendor ccf-paper-writer/references/ 2,586 行：storyline-blueprint 536、section-modules 261、research-writing-patterns 259、prose-quality-guardrails 124、length-budget-policy 125 ⋯⋯ 四跳外，且被明令「非必要不加载」

断点一：四跳链条，每一跳都是「可以」而不是「必须」

跳 1 paper-run stage prompt 「Read .agents/skills/section-writing/SKILL.md and follow it.」
「You may load these as sidecars alongside the owner skill.」
↓ 强制读到这里为止
跳 2 .agents/skills/section-writing/SKILL.md（95 行） 要求带上「the matching surface in scientific-writing.md」， 并「when the task is substantial drafting」把 ccf-paper-writer 当 sidecar 加载
↓ 条件判断，模型自行决定
跳 3 .agents/skills/ccf-paper-writer/SKILL.md（41 行，只是个 wrapper） 本体在 vendor 树：.agents/vendor/ccfa-skills/ccf-paper-writer/SKILL.md
↓ 又一跳，且 vendor SKILL.md 自带反加载规则
跳 4 vendor references/ — 17 个文件，2,586 行 vendor SKILL.md 原话：「Do not load venue guides, exemplar cards, citation workflows, storyline blueprints, section modules, length budgets, templates, or reviewer loops merely because they exist.」——最厚的 536 行 storyline-blueprint 被明确要求非必要不加载， 而 paper-run 的 prompt 从不给出「这次必要」的信号。
断点二 · 粒度

skill 按节设计，pipeline 按整篇调用

section-writing 全篇在讲「the active section」、「only the neighboring text needed for continuity」、「Do not load the complete manuscript」。但 paper-run 只有一个 canonical_drafting 阶段，45 分钟写完整篇。skill 的最小上下文纪律无从执行，模型只能略读后一口气全写——正是产出均质、平庸文本的典型形状。

断点三 · 顺序

两个润色 skill 挂反了

lieflat-less-ai-tone 自述是「final manuscript cleanup after writing is complete」，且 ccf-humanization 的阈值优先；vendor writer 要求「Run ccf-humanization as the first manuscript-facing preflight」。而 paper-run 把 lieflat 挂在 canonical_drafting，把 ccf-humanization 挂在 self_review——顺序正好反过来。

断点四 · 可执行性

质量检查器两边都够不着

runCheck() 把路径硬编码成 join(HARNESS.toolsDir, script)，只能跑 .agents/tools/ 下的脚本；check_prose_quality.py 在 vendor 树里，validator 够不到。而 writer agent 是 bash: ask 且被明令禁止跑脚本。结果是没有任何一方能运行它。

断点五 · 可观测性

没人知道 skill 到底读没读

系统不记录一轮里读了哪些 skill 文件，performance.json 只记 token 与成本。「skills 有没有被用上」这个问题目前在系统内无法回答，只能靠推断。这也意味着任何改进都无法验证是否生效。

断点六 · 未接入的设施

tools 里有五个脚本从未被调用

.agents/tools/ 下有 13 个受信任脚本，paper-run 的 stage 表只用了 8 个。check-venue-knowledge.py、check-documentation.py、check-reference-metadata.py、check-reference-corrections.py、check-release-records.py 从未出现在任何阶段。

断点七 · 会议知识

venue 是空的，默认退回 NeurIPS

vendor writer 的 Core Rule 是「Write for the target CCF venue, not for a generic paper」，缺省时退回 NeurIPS 指南并标注假设。material assessment 明明问了目标会议，但没有任何阶段把答案落进 .agents/knowledge/venues/。

三层分工

stages.ts 开头把这条边界写死了：harness 拥有怎么写论文， paper-run 拥有怎么把一个作业跑完。这也是控制器能保持成单个循环的原因—— 它从不知道「起草」是什么意思，只知道怎么跑一个阶段、校验它、然后过闸。

输入是什么

四类输入，按进入系统的时机排列
时机输入细节
init brief（必填） 可以是 brief 文件、BRIEF.md、或一个 brief 仓库目录。顺序很讲究：先拉模板 → 用 harness 真实校验器验 brief → 通过后才 commit。brief 不合格不会留下半初始化目录。
init mode / template / 仓库位置 / model --mode autonomous|collaborative、--template <tag>、--local 或 --repo owner/name。目标目录必须为空。
运行期 材料 契约 BRIEF.md + EXPERIMENTS.md，以及 materials/、evidence/、data/、figures/ 四个目录；递归深度 ≤ 3，最多 60 个文件——防止原始数据淹没 prompt，agent 可自行深入读。
每一轮 prompt 上下文 mode + 最近 4 条阶段历史 + 材料裁决 + 上一轮失败的校验项 + 人类在 gate 给的自由文本指导。

另外两个入口不走 init：paper-run transfer 把外部 TeX 仓库复制进隔离工作区， 抽取 title / author / abstract / bib / figure / build 元数据，未知项记为 unresolved，从不修改源仓库； paper-run review 做只出 findings 的冷评审，跑 review-report plan （只有 bootstrap + independent_review），永不进入 revision。

单个阶段内部的循环

控制器是一个循环、没有任何 per-stage 特例。阶段相关的东西全在 stage 表里， 模式相关的东西全在 gate 策略里，剩下这部分是无论哪种情况都必须正确的： 知道一轮什么时候真的结束、拒绝接受 agent 自称完成、以及让仓库在任何中断后都能续跑。

渲染 prompt→ 发给 agent→ 等 session.idle→ 锁定契约比对→ 跑 validators→ 失败则重试 ≤ retries→ gate→ Git checkpoint→ 推进
controller.ts

完成是观测出来的，不是声明出来的

控制器不读 agent 的散文找「done」信号，只等事件流的 session.idle，然后自己跑 harness 校验脚本。原话：没有有效 validator 的阶段，就是一个能悄悄什么都不产出的阶段。

prompts.ts

重试 prompt 具体到检查项名

不说「没通过，再试一次」，而是逐条列出失败的检查。并附一句关键的话：如果某个检查无法诚实满足就直说——失败的检查可以恢复，编造的结果不能。

controller.ts

每次退出都可恢复

状态在风险动作之前写。已通过校验但停在人类 gate 的阶段会 checkpoint 成 gate_waiting，resume 时直接回到那个 gate 重新校验，不重跑 agent；被中断且没 checkpoint 的阶段整个重跑。

locked-contract.ts

锁定契约 fail-closed

每轮前后对 PAPER.md 的 locked 字段和 BRIEF.md 做基线比对，被改就 block。人类要改需要 --authorize-locked-change <base-commit>:<digest>，且必须两个值都对得上。

controller.ts

gate 之后不许再动

通过 gate 后如果工作区还有额外变更，拒绝提交并报出具体文件名——避免把未经校验的改动顺手扫进 checkpoint。

permissions.ts

headless 遇权限请求立即失败

不隐形挂起。错误里带上请求的命令、pattern、阶段、session、request ID，并留在 run.json 里供 resume 诊断。

防造假是贯穿式的

这是整个系统最核心的价值取向，出现在四个层面。注释里给的理由是： 这是唯一一种「看似合理的结果比没有结果更糟」的失败模式，所以值得冗余。

层面机制
prompt 层 每个阶段的 ground rules 都重复 never fabricate；缺口的正确处理是 % TODO(paper-run): 标记加契约里的 unresolved。原话：带着诚实窟窿的稿子是这条流水线的正确输出。
裁决复核层 reconcileVerdict() 不信任 agent 自己填的 verdict 字段，而是从 assessment 自身数据重新推导：有 blockers 一律 unusable；research_question 和 evidence 都 absent 一律 unusable；声称 usable 但存在 absent 项则降级 partial。只降不升——因为模型在「要有用」的压力下更倾向高估就绪度。
硬停层 unusable 的阻断不走 gate 策略——autonomous 下所有 gate 都是 auto，靠 gate 会直接冲进起草。它是 isBlockedByUnusableMaterials() 这个独立谓词，每个阶段前都检查一次，resume 也走不过去。
权限层 paper-writer agent 明确 webfetch: deny / websearch: deny，禁止编辑 .agents/、.paper-run/、AGENTS.md、Makefile，不许自己跑 git 或校验脚本。写手只能用手上的材料，或者记一个 unresolved。

模式与 plan

模式只是 gate 策略的预设，不是两条代码路径。 autonomous 全部 auto；collaborative 在 6 个决策点暂停。 因为 mode 是一个值而不是控制流，中途切换会在下一个 gate 生效，不打扰正在飞的阶段。

gate 有两种打开方式：在 TUI 里回答 question picker，或者跑 /approve 写入 stage_status: approved。先到先得，另一边会被清理。 人类如果给的是自定义回答，会被当作 guidance 触发 revise，最多 3 轮。

plans.ts — 六个 profile，也可用 --stages 自定义
Profile包含的阶段
full全部 13 个
existing-manuscript跳过 evidence_inventory、story_outline、drafting、citation——用于已有稿子
review-and-revisebootstrap → material_assessment → self_review → independent_review → revision
review-report只有 bootstrap + independent_review，严格只出报告

review-only旧名兼容别名，等同 review-and-revise
plan 的四条硬约束

必须包含 bootstrap；必须保持流水线顺序且不重复； revision 依赖同一 plan 里有 independent_review； paper_candidate 依赖 publication_build。 plan 固化在 run.json 里，resume 不能悄悄改变作业范围。

利用现有设施提高写作能力

上一节的六个断点，指向同一个结论：不需要先去写新的写作方法论， 现有资产已经足够厚，缺的是把它们真正送到模型面前、并且能验证送到了。 下面按「杠杆 ÷ 成本」排序，全部只使用已经存在的设施。

  1. 先补可观测性，否则后面每一条都无法验证。 控制器已经在 waitForIdle 里订阅 OpenCode 事件流，只要把每轮的 read 类工具调用路径收集起来， 写进 performance.json，就能第一次回答「这一轮到底读了哪些 skill 文件」。 这是唯一一条必须最先做的——它把「skill 有没有被用上」从推断变成事实， 也是后面所有改动的 A/B 依据。
  2. 把 canonical_drafting 拆成按节的多轮。 section-writing 是按节设计的，现在被当整篇调用。stage 表是声明式的， 拆分不需要改控制器循环——每节一轮，各自带自己的 expectedOutputs 和 validator， 并且天然让 45 分钟的超时预算落在更可控的粒度上。这是最大的单点杠杆， 因为它同时解决了粒度错配和上下文超载。
  3. 把加载链条从「可以」改成「必须」，并绕过中间跳。 与其让模型沿着四跳自己走到 vendor 树，不如在 stage prompt 里直接给出这一节需要的 绝对路径：scientific-writing.md 的对应小节、 references/prose-quality-guardrails.md、 以及起草阶段的 references/storyline-blueprint.md。 vendor SKILL.md 的反加载规则说的是「不要仅仅因为存在就加载」—— 由 prompt 显式点名，正是它要求的那个「任务确实需要」的信号。
  4. 把 check_prose_quality.py 接成 validator。 它已经是成品：读文件、输出 JSON、--strict 给退出码， 检测填充开头、精确性词汇、em-dash 密度、句长均匀度、段落均匀度、分号密度。 接法有两种——放宽 runCheck() 允许 vendor 下的受信任脚本， 或在 init 时把它纳入 .agents/tools/。建议先以 required: false 上线， 积累几轮真实分布再决定阈值。这是唯一一个能让「写得好不好」进入 validator 的现成入口。
  5. 把两个润色 skill 的顺序摆正。 ccf-humanization 前移到 canonical_drafting 作为 preflight， lieflat-less-ai-tone 后移到 self_review 之后作为最终白名单 pass。 这是改两行 sidecar 声明的事，但它让两个 skill 各自回到自己设计的位置上。
  6. 让 venue 知识真正落地。 paper_positioning 阶段已经在定「写给谁」，让它同时产出 .agents/knowledge/venues/<venue>.md， 然后挂上已经存在但从未被调用的 check-venue-knowledge.py 做校验。 这样 vendor writer 的「Write for the target venue」才有东西可依， 不必默默退回 NeurIPS 兜底。
  7. 让 review 的产出可机器消费。 现在 review-findings.md 只被检查「有三节且非空」。 改成结构化输出后，控制器就能强制「每条 blocker 在 revision 后要么消失、要么有显式 deferral 理由」， 而不是把这件事托付给下一轮模型的自觉。顺序上排在后面， 因为它的收益依赖前面几条先把稿子质量抬上来。
